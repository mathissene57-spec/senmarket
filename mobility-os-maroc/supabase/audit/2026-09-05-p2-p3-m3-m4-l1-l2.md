# P2/P3 : M-3 (avis_courses), M-4 (pg_net), L-1 (anti-bot OTP), L-2 (donnees GPS publiques)

## M-4 : extension pg_net enregistree dans le schema public

**Constat (advisor Supabase, `extension_in_public`, WARN)** : `pg_net` est
enregistree dans le schema `public` (`pg_extension.extnamespace = public`).

**Tentative de correction** : `alter extension pg_net set schema extensions;`
echoue avec `ERROR: 0A000: extension "pg_net" does not support SET SCHEMA` --
pg_net n'est pas relocalisable (limitation connue et documentee cote
Supabase, qui indique travailler sur une resolution future ; ce n'est pas
une negligence de configuration de ce projet).

**Analyse de risque reel** : les fonctions effectivement appelees par ce
projet (`net.http_post`, utilisee par `declencher_push()` et
`envoyer_sms_otp()`) vivent deja dans leur propre schema dedie `net`, cree
par l'extension elle-meme independamment du schema ou l'extension est
enregistree. Aucun appel du code applicatif ne passe par `public.` pour ces
fonctions. L'exposition reelle de ce WARN est donc cosmetique : elle ne
donne acces a aucune fonction/donnee supplementaire a un role qui n'y
aurait pas deja acces autrement.

**Decision** : ne pas forcer un `DROP EXTENSION` / `CREATE EXTENSION pg_net
SCHEMA extensions` pour contourner la limitation -- cette operation
supprimerait et recreerait les tables de file d'attente internes de pg_net
et pourrait interferer avec la gestion de l'extension par la plateforme
Supabase elle-meme (Database Webhooks, si actives sur ce projet), pour un
gain de securite nul. Gap accepte et documente, a revisiter si Supabase
publie une version relocalisable de pg_net.

## M-3 : avis_courses lisible integralement par anon, sans aucun filtre

**Constat** : `avis_courses (id, course_id, note, commentaire, created_at)`
a une seule policy, `avis_lecture_publique` (`PERMISSIVE`, roles `{public}`,
`cmd SELECT`, `qual = true`) -- absolument aucune restriction. N'importe qui,
sans authentification, peut executer `GET /rest/v1/avis_courses?select=*`
et recuperer en une seule requete (paginable) l'integralite des avis de la
plateforme, tous operateurs confondus, y compris le champ `commentaire`
(texte libre redige par le passager).

**Ce qui est legitime** : afficher les avis d'un chauffeur/operateur est une
fonctionnalite produit normale (comme n'importe quelle marketplace) -- ce
n'est pas la lisibilite en soi qui pose probleme.

**Ce qui ne l'est pas** : (a) aucun filtre de scope (le client peut lire les
avis de tous les operateurs en un seul appel, pas seulement ceux d'un
chauffeur/operateur donne qu'il consulte legitimement) ; (b) le champ libre
`commentaire` peut contenir des informations que le passager n'aurait pas
voulu voir agregees/scrapees en masse (un passager mecontent peut ecrire
des details identifiants dans son commentaire) ; (c) aucune limite de debit
cote PostgREST -- un scraping complet et repete de la table est trivial.

**Decision** : corrige (contrairement a M-4). Verification prealable : un
`grep -r avis_courses webapp/` ne renvoie aucun resultat -- aucune page du
depot n'interroge cette table directement aujourd'hui, donc fermer l'acces
direct ne casse aucune fonctionnalite existante. Decouverte en tentant
d'ajouter une fonction scopee equivalente : `avis_chauffeur(p_chauffeur_id
uuid, p_limite integer)` **existe deja en production** (SECURITY DEFINER,
meme patron que `chauffeurs_operateur()`/`courses_operateur()`, deja
plafonnee entre 1 et 100 avis, deja executable par anon/authenticated) --
elle n'avait simplement jamais ete accompagnee de la fermeture de l'acces
direct a la table brute, qui restait donc un contournement total (lecture
de TOUS les avis de TOUS les operateurs en un seul appel, sans passer par
le scope ni la limite de cette fonction). Migration
`20260905110000_p2_m3_avis_courses_scope_par_chauffeur.sql` : `revoke
select on avis_courses from anon, authenticated`, sans creer de nouvelle
fonction (celle qui existe deja suffit).

## L-1 : aucune limite anti-bot au-dela du numero de telephone sur demander_otp

**Constat** : `demander_otp()` limitait deja le debit par numero (3
demandes / 10 min / numero, cf. audit initial), mais aucune limite globale
tous numeros confondus. Un bot capable de faire tourner de nombreux numeros
differents (achetes, generes, ou simplement incrementes) pouvait donc
declencher un envoi de SMS reel illimite au niveau de la plateforme
entiere, une fois un vrai fournisseur SMS branche (C-1/`envoyer_sms_otp`) --
un vecteur de fraude connu ("SMS pumping fraud") qui se traduit directement
par une facture fournisseur qui explose.

**Decision** : corrige. Migrations
`20260905120000_p3_l1_limite_globale_anti_bot_otp.sql` puis
`20260905130000_p3_l1_correction_exemption_numeros_demo.sql` (correction
appliquee le meme jour, avant tout commit git -- la premiere version
comptait aussi les numeros de demo utilises par la suite de regression,
ce qui aurait fait echouer la suite elle-meme). Version finale : un
coupe-circuit rejette toute nouvelle demande des que 20 demandes reelles
(numeros hors liste de demo) ont ete emises sur la derniere minute, tous
numeros confondus. Seuil choisi largement au-dessus du trafic legitime
attendu pour un pilote (quelques operateurs, quelques dizaines
d'utilisateurs actifs) -- purement une premiere ligne de defense au niveau
base de donnees ; une protection complementaire au niveau infrastructure
(WAF/rate-limiting par IP en amont, ex. Vercel/Cloudflare) reste
recommandee pour la mise en production reelle (P6).

## L-2 : coordonnees GPS et adresses exactes de toutes les courses actives lisibles par quiconque

**Constat** : la policy `courses_lecture_recente` (necessaire au dispatch
temps reel pour des apps passager/chauffeur sans session Supabase Auth,
deja documentee comme limite assumee lors de P0.2) expose, a n'importe qui
sans authentification, TOUTES les colonnes de `courses` pour toute course
recente (6 statuts, fenetre de 6h), tous operateurs confondus -- y compris
`depart_lat`/`depart_lng`/`arrivee_lat`/`arrivee_lng` (coordonnees GPS
exactes) et `adresse_depart`/`adresse_arrivee` (texte libre, potentiellement
domicile/travail du passager).

**Pourquoi ce n'est pas corrige ici** : contrairement a M-3, il n'existe pas
de restriction de colonnes possible sans casser la fonctionnalite legitime
-- l'app passager a elle-meme besoin de lire ces memes colonnes pour
afficher SA PROPRE course active sur la carte. Le probleme est le perimetre
(toutes les courses de tous les operateurs sont visibles, pas seulement
celle du passager consultant), pas les colonnes elles-memes. Une correction
reelle necessite de remplacer `postgres_changes` (qui exige une ligne
lisible par RLS pour etre livree via Realtime) par **Realtime Broadcast +
Authorization** (canaux prives scopes par course, cf. recommandation deja
notee dans `supabase/tests/regression.sql`, test P0.2b) : un changement
d'architecture qui touche le schema (triggers de broadcast), le frontend
(passager/page.tsx et chauffeur/page.tsx, remplacement de
`.on('postgres_changes', ...)` par `.on('broadcast', ...)`), et qui ne peut
pas etre valide de bout en bout dans ce bac a sable (acces reseau a
Supabase Realtime bloque par la politique reseau de l'environnement, cf.
tache #6). Tenter cette migration maintenant, sans pouvoir la tester
reellement contre des apps en cours d'execution, ferait courir un risque
disproportionne a la fonctionnalite la plus critique de la plateforme (le
dispatch temps reel) au regard du principe "modifications minimales,
testables et reversibles". Gap accepte et documente ; a traiter en priorite
lors de P6 (durcissement production) ou P7 (UX mobile reelle), une fois la
QA fonctionnelle reelle (P4) possible sur un environnement avec acces
reseau complet.
